# v0.6.0 — Check the mods on disk, close your terminal, and a delete that refuses to run wild

This release is mostly about the install *after* it's installed: proving it's
still intact, refusing to damage it, and explaining itself when a launch fails.

## `verify` — is what's on disk still what was installed?

`check-md5` already answered "did the download arrive correctly" by comparing
the **archives** in `gamma/downloads` against published sums. It said nothing
about what actually sits on disk. A mod file corrupted later, overwritten by
another tool, or truncated by a full disk was invisible — even though "the game
crashes since yesterday" is the first thing a player reports.

```sh
stalker-gamma-linux verify           # report differences
stalker-gamma-linux verify --repair  # reinstall only the mods that differ
```

It's in the window too, as two buttons in the Diagnostic view — same code path,
no separate GUI logic.

Two behaviours worth knowing before you run it:

- **The first run records, it doesn't verify.** With no earlier reference there
  is nothing to compare against, and reporting "no differences" would suggest a
  check that never happened. The reference lands next to the install as
  `gamma-md5.txt`, so it follows the install rather than living under
  `~/.config`.
- **A cancelled scan can't become the new reference.** Ctrl-C raises instead of
  returning a partial result, so a broken install can't be frozen in as the
  baseline.

`--repair` deletes and reinstalls the affected mod folders. Files that are
*added* (present on disk, absent from the reference) are never repaired, and
neither is the folder containing them.

## `play` no longer holds your terminal hostage

Launching from the command line used to tie the game's life to the terminal
window: closing it sent SIGHUP and killed the game. `play` now detaches, prints
the path of its launch log, and returns immediately.

Getting there took two passes, and the second is the interesting one.
`start_new_session=True` alone wasn't enough: umu-run's internal sandbox
(`srt-bwrap`) calls `setsid()` itself and then claims the inherited stdin as its
*own* controlling terminal — so closing the window still killed Proton, Wine,
MO2 and the game, one layer further down. Cutting stdin (`DEVNULL`) closes that
path. Verified on a real install, all the way to `AnomalyDX11.exe` surviving the
terminal's death.

**Behaviour change**: `play` no longer waits for the game to exit, so it can no
longer diagnose USVFS afterwards — `--no-diagnose` is gone with it. The
after-the-fact diagnosis is still available from the launch log.

## Launch failures that explain themselves

When the game doesn't start, the launch log now gets read for the two failures
that happen *before* USVFS ever gets a chance:

- missing VC++ 2015-2022 runtimes in the prefix → `prefix-doctor --repair`;
- a prefix built by a different Proton version → `install --only prefix`.

Either one is reported *instead of* the USVFS diagnosis, not alongside it: a
user told about two problems fixes neither.

## Refusing to damage the install

Two guards, both structural rather than advisory:

- **`uninstall --game-data` no longer trusts `--target`.** It was passed
  straight to `rmtree` with the failure swallowed — `--target ~` was enough to
  walk off with `$HOME`. Refusals now cover system roots, `$HOME` and its
  neighbours, the current directory, the repo and venv in use, relative paths,
  symlinks and insufficient depth, and on top of all that require an actual
  install marker (`anomaly/`, `gamma/`, `prefix/`, a state file). The target is
  resolved once and *that* path is what gets deleted, so no TOCTOU reopens
  between the check and the removal. An interactive confirmation was added
  (resolved path, estimated size), with `--yes` for scripted use.
- **Nothing destructive runs on a prefix that's in use.** `prefix-doctor
  --repair`, `update`, `install --only prefix` and `uninstall --game-data` now
  detect a live prefix — via wineserver (which catches "MO2 closed but the game
  is still running"), then MO2, then the game executables — and refuse. `--force`
  overrides. If `/proc` or `pgrep` are unavailable the answer degrades to "not
  busy", so a missing diagnostic tool never blocks you.

## Arch packages, actually built

`packaging/aur/` shipped as written-but-unproven in v0.5.0. Both PKGBUILDs
(`python-gamma-launcher` and `stalker-gamma-linux`) are now **built and verified
under `archlinux:latest`**, producing the binaries, the menu entry, the hicolor
icon and the licence, with the test suite running inside `check()`.

Nothing is published to the AUR: that reserves a name on a public repository and
engages an account, so it stays a maintainer decision. The steps are in
`packaging/aur/README.md`.

## Also

- The `WINESERVER` question under umu is settled and written up in
  `docs/MO2-PROTON-COMPAT.md`: no client/server decoupling exists on this path,
  so nothing was pinned. Measured across three real launches (GE-Proton11-3,
  GE-Proton9-20, GE-Proton11-1) by reading both `/proc/<pid>/environ` and
  `/proc/<pid>/exe` — the env says what was asked, the exe link says which binary
  won. The container replaces `/usr`, which makes the host's wineserver
  unreachable in the first place.
- That write-up also corrects a wrong cause in the symptom table: the Wine
  "version mismatch" family comes from Proton's prefix-version check, not from
  wineserver selection.
- CI repair: `pytest -q` had been failing collection since the integrity tests
  landed (the bare `pytest` script doesn't put the repo root on `sys.path`, which
  `python -m pytest` hid locally), and `ruff format --check` was failing on a
  docstring line left at column 0. Both fixed — the release gate runs these.

## Upgrading

```sh
curl -fsSL https://raw.githubusercontent.com/Fleorens/stalker-gamma-linux/main/install.sh | bash
```

or `./install.sh --no-launch` from an existing checkout. Your game, mods and
saves are untouched.
