# Clôture transitive épinglée : la liste exacte de ce que `pip install .`
# installe, versions comprises.
#
# POURQUOI CE FICHIER
# `gamma-launcher` déclare ses neuf dépendances sans AUCUNE borne de version, et
# nos deux dépendances directes n'avaient qu'un plancher (`rich>=13.0` résolvait
# déjà en 15.x, deux majeures plus haut). Sans épinglage, deux installations
# lancées à une semaine d'écart n'installent pas le même code, et aucune n'est
# auditable après coup : on ne sait pas dire ce qui tournait chez un utilisateur
# qui rapporte un bug, ni si une version compromise est passée (CWE-1104).
#
# C'est un fichier de CONTRAINTES, pas de `requirements` : il n'installe rien
# par lui-même, il impose seulement une version à ce que la résolution touche
# déjà. `pyproject.toml` reste la seule source de vérité sur « qui dépend de
# quoi » — ici il n'y a que des « laquelle ».
#
# CE QUI N'Y FIGURE PAS, ET POURQUOI
# `install.sh` crée le venv avec `--system-site-packages` : PyGObject (GTK4 /
# libadwaita) n'a pas de roue pip et vient obligatoirement du paquet distro.
# Ce fichier ne nomme donc QUE la clôture de nos propres dépendances — ni
# PyGObject, ni pycairo, ni quoi que ce soit que la distribution installe pour
# elle-même. Les y mettre forcerait pip, sur toute machine dont la version
# distro diffère du pin, à reconstruire une extension liée à
# GObject-introspection depuis les sources : échec garanti sans les en-têtes de
# développement, sur la machine d'un joueur qui n'a rien demandé.
#
# Corollaire à connaître quand une dépendance de la liste est AUSSI fournie par
# la distribution (Fedora 44 : requests, beautifulsoup4, urllib3, psutil…) et
# que sa version diffère du pin : pip installe la version épinglée DANS le venv.
# Le paquet système n'est ni touché ni rétrogradé — pip n'écrit jamais hors du
# venv et `install.sh` ne demande jamais sudo ; le venv voit simplement notre
# copie en premier.
#
# Pas de `--require-hashes` : pip exige alors un hash pour TOUTES les exigences,
# y compris la référence git de `gamma-launcher`, qu'il refuse par construction
# de hasher. Le SHA de commit épinglé dans `pyproject.toml` tient ce rôle pour
# elle ; pour le reste, PyPI ne remplace jamais l'artefact d'une version publiée.
#
# RÉGÉNÉRER (à chaque changement de dépendance, et seulement là) :
#   python3.11 -m venv /tmp/closure     # NU : surtout pas --system-site-packages
#   /tmp/closure/bin/pip install .
#   /tmp/closure/bin/pip freeze --exclude-editable
# Le venv doit être nu : avec les paquets du système visibles, pip n'installe
# pas ce que la distro fournit déjà et le `freeze` rend une clôture trouée.
# Et sur le plus VIEUX Python supporté (3.11), parce que la clôture y est la
# plus large : py7zr n'y ajoute `backports.zstd` que sous 3.14, où la stdlib
# fournit `compression.zstd`. Un venv 3.14 produirait une liste incomplète pour
# Debian 12 et Ubuntu 24.04. Vérifié : 3.11, 3.12 et 3.14 résolvent des versions
# identiques, `backports.zstd` mis à part.

# Dépendances directes (pyproject.toml). `gamma-launcher` s'installe depuis une

# l'install échoue net si un jour ce n'est plus le cas.
